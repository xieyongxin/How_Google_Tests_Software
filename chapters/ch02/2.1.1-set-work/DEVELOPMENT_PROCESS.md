# 开发过程：模拟 Google 的 SWE 与 SET 协作

这份文档记录 Demo 的实际编写流程。它不是事后拼出的功能清单，而是与 Git 提交同步维护的工程日志。每个阶段都说明负责角色、交付物和质量验证方式。

## 角色约定

- **SWE（Software Engineer）**：设计接口、实现产品代码，并为自己负责的构建目标编写基础小型测试。
- **SET（Software Engineer in Test）**：参与设计，发现可测试性和覆盖缺口，建设 mock/fake，补充小型及中型测试。
- **构建工程角色**：把编译、静态分析和各层测试组织成所有人都能重复执行的统一入口。

这不是传统的“开发写代码、测试包办验证”。质量属于整个工程团队，SET 的价值在于提升团队的测试能力和工程效率。

## 阶段记录

### 阶段 1：明确目标

- 提交：`文档：整理SET工作要点与订单实践流程`
- 决策：每节使用独立工程，保留能逐步复盘的中文提交。
- 决策：采用接口先行；SWE 编写基础单元测试；SET 补充测试点、fake 和集成测试。
- 结果：章节总结、概念映射和七阶段实践路线已建立。

### 阶段 2：接口先行

- 提交：`开发：定义订单系统服务接口和构建目标`
- SWE 交付：库存与支付接口，以及四个边界清晰的 Maven 构建目标。
- 依赖方向：订单服务只依赖 `service-contracts`，尚不依赖任何具体库存或支付实现。
- 验证命令：`mvn clean compile`
- 结果：聚合工程与四个模块均可独立编译。

### 阶段 3：SWE 交付功能与基础测试

- 提交：`开发：实现订单服务并添加基础单元测试`
- SWE 交付：订单请求、处理结果和协调库存与支付的订单服务。
- 小型测试：使用 Mockito 隔离外部依赖，验证成功下单和库存不足两条核心路径。
- 验证命令：`mvn test`
- 结果：SWE 编写的 2 个单元测试通过，其他模块仍可正常构建。

### 阶段 4：SET 补充测试能力

- 提交：`测试：补充边界场景和模拟依赖工具`
- SET 评审：核心路径已有覆盖，但支付失败后的库存一致性、非法输入和禁止多余调用尚未验证。
- 补充测试：支付拒绝时释放库存；非法数量、金额和空请求不接触外部依赖。
- 测试工具：实现内存库存 fake 和可配置、可记录调用的支付 fake，并为共享 fake 添加自己的单元测试。
- 验证命令：`mvn test`
- 结果：订单服务 6 个小型测试、fake 服务 3 个小型测试全部通过。

### 阶段 5：SET 添加中型集成测试

- 提交：`测试：添加订单系统跨模块集成测试`
- 测试边界：使用真实 `OrderService`、内存库存 fake 和支付 fake，不检查实现内部的方法调用细节。
- 集成场景：成功下单会扣减库存并记录支付；库存不足不会支付；支付拒绝会恢复库存。
- 验证命令：`mvn -pl order-app -am test-compile failsafe:integration-test failsafe:verify`
- 结果：3 个中型集成测试通过，同时之前的 9 个小型测试继续作为回归测试运行。

其余阶段将在实际实现和验证后补充。
