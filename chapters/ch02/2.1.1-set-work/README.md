# 2.1.1 SET 的工作：迷你订单系统实践

本项目不是为了展示复杂的订单业务，而是用一个足够小的系统模拟书中描述的 Google 开发与测试流程。代码会按照接口、实现、小型测试、测试工具、中型测试、统一工程检查和可运行产品的顺序逐步提交。

## 内容总结

### 质量由整个工程团队负责

SET 和 SWE 是紧密合作的伙伴，工作会有重叠。SWE 不只是交付功能代码，也负责大部分小型测试；SET 帮助识别遗漏的测试点、改善可测试性、建设 mock 和 fake，并在多个构建目标集成后编写中大型测试。测试不是开发之后的附加活动，而是产品功能的一部分。

### 统一环境降低工程成本

统一代码库、构建工具、编译器、运行平台和打包规范，使工程师可以快速切换项目、复用公共代码，并让开发机、测试机与生产环境中的行为尽量一致。减少环境差异，本质上是在减少难以定位的下游问题。

### 公共代码需要更高标准

共享代码应当容易发现、容易阅读、可独立复用，并显式声明依赖。修改公共代码时需要考虑所有使用者，通过代码审核，并提供比普通业务代码更充分的测试。相比复杂或巧妙的设计，可复用性和可维护性更有长期价值。

### 构建目标推动增量开发

开发从较小的库构建目标开始，同时创建配套的测试目标。随着服务逐渐组合成更大的应用，原有小型测试成为持续运行的回归测试，SET 再增加覆盖服务协作的中大型测试。任何本应通过却失败的测试，都应像功能缺陷一样得到修复。

### 接口先行支持并行开发

服务间接口在项目早期确定。依赖方针对约定接口开发，而不是等待真实服务完成；尚未实现的服务由 fake 替代。这让各个服务能够并行构建、打包和测试，最终再组合为产品。

## Demo 如何映射书中实践

| 书中的做法 | Demo 中的实现 |
| --- | --- |
| 服务接口尽早确定 | `service-contracts` 首先定义库存和支付接口 |
| 公共代码和依赖显式声明 | 各 Maven 模块只声明直接依赖 |
| SWE 编写功能和小型测试 | `order-service` 使用 JUnit 和 Mockito 验证核心路径 |
| SET 补足测试能力 | SET 阶段增加边界测试和可复用 fake |
| 构建目标逐步组合 | 四个 Maven 模块从接口库组合到命令行应用 |
| 小型测试成为回归测试 | 每次 `mvn verify` 都重新运行单元测试 |
| SET 编写中大型测试 | `order-app` 的集成测试使用真实业务库与 fake 服务 |
| 统一工具和质量门禁 | Maven 统一运行 Checkstyle、SpotBugs、单元和集成测试 |

## 构建与运行

环境要求：JDK 21、Maven 3.9 或更高版本。

在本目录执行完整质量验证：

```shell
mvn clean verify
```

只验证订单服务及其依赖：

```shell
mvn -pl order-service -am test
```

运行打包后的命令行应用：

```shell
java -jar order-app/target/order-demo.jar
```

一次成功下单会输出 `status=SUCCESS`、非空确认号、`remainingStock=3` 和 `paymentAttempts=1`。

## 按开发过程学习

不要只阅读最终代码。按提交顺序观察系统如何增长：

```shell
git log --reverse --oneline
git show <提交哈希>
```

建议在每个提交上执行当时记录的验证命令，比较 SWE 的基础测试、SET 补充的边界测试和跨模块测试分别发现什么问题。完整轨迹与每阶段结果见 [DEVELOPMENT_PROCESS.md](DEVELOPMENT_PROCESS.md)。
