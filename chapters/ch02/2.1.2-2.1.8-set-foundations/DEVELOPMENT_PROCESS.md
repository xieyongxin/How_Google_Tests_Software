# 开发过程：SET 基础职责与项目早期

本实验按书中的项目演化顺序推进，而不是先写完整系统再补一份测试说明。每条提交都代表一个角色可以交付和审查的工作单元。

## 角色

- **项目发起人**：说明用户问题、价值假设和概念验证成功标准。
- **Tech Lead**：确定系统边界、记录技术决策，并维护设计文档的整体一致性。
- **SWE**：实现最小原型，并为稳定的纯函数路径编写基础小型测试。
- **SET**：以工程师身份参与设计评审，识别可测试性风险，提出接口、错误注入和自动化建议。

## 项目阶段边界

概念验证阶段只回答“这个想法是否值得继续”：使用内存索引、最少依赖和少量测试。正式立项后的网络服务、Protobuf 协议、HTTP 端到端测试和持久化索引属于下一个实验，不在本目录提前实现。

### 阶段 1：文档与角色约定

- 提交：`文档：建立SET角色与项目早期实践说明`
- 团队交付：章节总结、设计文档骨架、角色边界、测试计划和书本映射。
- 结果：明确概念验证与正式立项的边界，后续每个角色都有可审查的交付物。

### 阶段 2：设计 AddUrl 概念项目

- 提交：`设计：编写AddUrl项目设计文档与团队结构`
- Tech Lead/SWE 交付：目标、非目标、最小系统边界、风险、路线图和验收标准。
- 验证：人工按完整性、正确性、一致性、设计、接口和测试六个维度进行评审。

### 阶段 3：SET 可测试性评审

- 提交：`设计：补充可测试性与自动化计划评审`
- SET 交付：依赖注入、接口隔离、错误注入、超时控制、测试钩子和自动化范围的评审意见。
- 自动化策略：先覆盖高风险接口和快速反馈路径，再增加少量中型、大型测试。
- 验证：`python scripts/check_design_document.py`
- 结果：设计文档必需部分齐全，所有暂不实现的建议都有后续阶段归属。

其余阶段将在实现和验证后补充。
